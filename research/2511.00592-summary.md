# Agentic Auto-Scheduling: An Experimental Study of LLM-Guided Loop Optimization

- **Authors:** Massinissa Merouani, Islem Kara Bernou, Riyadh Baghdadi — New York University Abu Dhabi
- **Venue:** PACT 2025 (34th Int'l Conf. on Parallel Architectures and Compilation Techniques), IEEE
- **arXiv:** 2511.00592 (v2, Dec 27 2025) · PDF: `2511.00592-agentic-auto-scheduling.pdf`

## Core idea
Asks whether off-the-shelf LLMs, grounded in empirical compiler feedback, can guide loop
optimization **without any fine-tuning**. Their answer is **ComPilot** ("Compiler Pilot"): an LLM
acts as an **optimization agent** in a **closed feedback loop** with a compiler. The LLM proposes a
sequence of loop transformations (a "schedule"); the compiler (here **Tiramisu**, a polyhedral
compiler) applies them, checks legality via dependence analysis, generates + runs code, then reports
back *legality status* and *measured speedup/slowdown*. The LLM refines its strategy from this feedback.

Crucial design choice: the LLM only emits high-level transformation commands — it **never writes the
optimized code**. The compiler handles codegen and **formally guarantees correctness**. LLM does
strategic exploration; compiler does rigorous verification.

## How it works
1. **Context Initialization** — constant system prompt defines role, I/O format, transformation
   repertoire, hardware details, crash handling. Target loop nest is presented in standardized,
   **anonymized** C/C++ form. LLM first **analyzes** the loop nest (chain-of-thought) before proposing.
2. **Iterative Optimization** — LLM proposes schedules in `<schedule>...</schedule>` tags with reasoning.
   Two-stage check: lightweight validity pre-filter, then **formal polyhedral legality check**.
   Feedback categories: *Invalid*, *Illegal*, *Solver Failure*, *Compiler Crash*, *Successful Execution*
   (with measured speedup). Loops until LLM stops or iteration limit.

**9 transformation primitives:** Fusion, Shifting, Interchange, Parallelization, 2D Tiling, 3D Tiling,
Unrolling, Skewing, Reversal.

## Experimental setup
- **Hardware:** dual-socket 2×12-core Intel Xeon E5-2695 v2 @2.4GHz, 48 threads, 128 GB RAM.
- **Primary LLM:** `gemini-2.0-flash` (8 LLMs compared total).
- **Benchmarks:** PolyBench/C 4.2.1 — 30 kernels × 5 dataset sizes = **150 instances**.
- **Methodology:** 40 independent runs/instance; report **median** per instance, **geometric mean**
  across instances, bootstrapped 95% CIs. Notation: `ComPilot@T` = single-run median after T iterations;
  `ComPilot_K@T` = best-of-K.

## Key results (by research question)
- **RQ1 — Speedups:** `ComPilot@30` = **2.66× geomean** over original (single run); best-of-5 = **3.54×**.
  Highly skewed: some kernels >100× (`correlation_XLARGE` 339×, `trmm_XLARGE` 183×). A few
  dependency-heavy kernels (cholesky, durbin, ludcmp) ≈ 1× (no gain).
- **RQ2 — Cost:** Token usage grows **non-linearly** (~200k tokens by iter 30; full dialogue resent each
  turn). ~8.9 min/instance for 30 iters, but **~78.5% is the compiler** (legality + compile + run); LLM
  comms only 1–3 min.
- **RQ3 — Proposal quality:** 36.1% runnable, 31.4% invalid, 32.5% illegal. Illegal rate starts ~60% at
  iter 1 and **drops as the LLM learns** — evidence of in-context learning.
- **RQ4 — Different LLMs:** Top: `gemini-2.0-flash` (2.66×), `gpt-4o` (2.63×), `gpt-o3-mini` (2.57×).
  Reasoning models did **not** consistently beat non-reasoning; coding-specialized models underperformed
  (qwen2.5-coder 2.14×, codestral 1.75×). Older models couldn't follow the format and were excluded.
- **RQ5 — vs. Pluto (SOTA polyhedral optimizer):** best-of-5 beats Pluto by **2.94× geomean**, winning
  119/150 instances. Largest advantage on small inputs (MINI 16.35×), shrinks/reverses on large (XLARGE
  0.82× slowdown). Wins because it optimizes *measured* performance and avoids Pluto's harmful heuristic
  decisions (e.g., `trisolv`). Also beats Tiramisu's DL autoscheduler (2.65× / 3.23×) on 8 supported kernels.

## Ablations (what matters)
- **RQ6 — Feedback is essential:** removing the loop drops performance ~23% (single-run) to ~40% (gpt-4o).
- **RQ7 — Delegating codegen to the compiler matters:** LLM-writes-C alternative is ~14–16% slower *and*
  dangerous — 17.6% of "successful" schedules gave **incorrect output** under random inputs despite passing
  checks; also ~5.3× more tokens.
- **RQ8 — Hardware context in prompt:** no statistically significant effect; feedback loop dominates.
- **RQ9 — Scaling:** diminishing returns in iters (1.41× → 2.66× → 3.06× at T=1/30/75) and runs
  (2.66× → 3.54× → 3.82× at K=1/5/13). Chose T=30, K=5.
- **RQ10/RQ11:** chain-of-thought helps (~8% from initial analysis); nudging LLM past premature stops helps.

## Limitations & future work
~2/3 of proposals are unproductive (invalid/illegal); multiple runs needed to escape local optima;
non-trivial token/compute cost. Future: **richer feedback** (which dependency was violated; hardware perf
counters like cache-miss/vector-lane utilization so the LLM learns *why* a schedule is faster), hybridizing
with systematic search, dialogue summarization for context length. Paradigm is **backend-agnostic** — could
drive GCC/Clang pragmas or LLVM passes, not just Tiramisu.

## Bottom line
General-purpose LLMs, **without fine-tuning**, can be effective compiler-optimization agents when placed in
a closed loop with a compiler that guarantees legality and measures real performance — beating both the
original code (3.54×) and the SOTA Pluto optimizer (2.94×) on PolyBench.
